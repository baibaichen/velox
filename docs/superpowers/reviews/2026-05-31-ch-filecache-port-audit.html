{

        code == /*ENOSPC*/28 || code == /*EDQUOT*/122;
    auto lk = lock();

LOW F7 FileCacheKey 哈希不同（SpookyHashV2 vs SipHash128） 已文档化
三方评级 — GPT-5.5: M · Claude-detailed: L · 独立: (折叠)  |  有意替换；非 bug。影响更正 2026-05-31：跨重启可复用
ClickHouse — sipHash128（固定零 key）
// FileCacheKey::fromPath(path): sipHash128(path.data(), path.size())
Velox — SpookyHashV2（固定种子 0,0，同为确定性哈希）
FileCacheKey FileCacheKey::fromPath(const std::string& path) {
  uint64_t h1 = 0, h2 = 0;
  // CH uses sipHash128; we pin SpookyHashV2 (fixed seed 0,0). Both are
  // deterministic -> keys ARE stable across restarts of the same binary.
  // Only limitation: different algorithm than CH, so the cache directory
  // cannot be shared with a real ClickHouse instance.
  folly::hash::SpookyHashV2::Hash128(path.data(), path.size(), &h1, &h2);
  return FileCacheKey((static_cast<UInt128>(h1) << 64) | h2);
}
影响：更正：两者在固定 key/seed 下都是确定性哈希 → 同一路径同一二进制产出同一 key，跨进程重启稳定可复用（配合 initialize()→loadMetadata() 重扫目录）。唯一真实限制是算法不同 → 缓存目录无法与真实 ClickHouse 互通；进程内/跨重启复用不受影响。原代码注释「NOT reusable across restarts」措辞过宽，将修正。

其余条目

LOW F9 短对象 EOF 被当作下载失败 集成层
来源 — Claude-d/独立
CH 把「远端对象在 listing 与读取间变短」视为合法 EOF（setDownloadFinishedWithoutContinuation）；Velox 源端无前进即 setDownloadFailed→VELOX_FAIL。最终段状态等价；DWIO 读 region 源于已知 fileSize_，正常不越界，触发概率低。
MEDIUM F10 DETACHED bypass 粒度：region 级 vs CH per-segment 集成层
来源 — 独立
CH 仅当前 DETACHED 段走 bypass；Velox region 内任一段 DETACHED 则整个 region 全量 pread。其他已缓存段被一并绕过 → 命中率/性能下降（数据不损坏）。
MEDIUM F11 段完成 / 空间释放时机：持有到 BufferedInput 析构 集成层
来源 — 独立
CH 边读越过段边界即逐段 complete；Velox 段 holder 存于 enqueuedRegions_，仅在 BufferedInput 析构时 completeAndPopFront。后台 tail-fill / shrink / 空间释放 / 优先级推进时机推迟。
LOW F12 origin user 每进程随机 vs CH ServerUUID 核心层
来源 — 独立
CH 用配置 user 或 ServerUUID（跨重启稳定）；Velox 用随机 FileCacheKey（每进程随机）。若依赖按 user 划分目录则跨重启不忠实。
LOW F13 write 打开 flags 丢 O_APPEND / O_CLOEXEC（功能仍正确） 集成层（等价）
来源 — 独立
CH 续写用 O_WRONLY|O_APPEND|O_CLOEXEC；Velox 计算 flags 后 unused(flags)，LocalWriteFile 用 O_WRONLY|O_CREAT + lseek(SEEK_END) 续写不截断。仅损失 append 原子性与 close-on-exec，单 downloader 顺序写无实际问题。
LOW F14 删文件后 OpenedFileCache fd 清理未移植（当前无风险） 核心层
来源 — Claude-d
CH 删段文件后清 OpenedFileCache 的 fd；Velox 仅 TODO。读路径每次 new LocalReadFile，无 fd 缓存，故当前无实际风险。
LOW F15 可观测性 metrics / ProfileEvents / failpoint 成片 TODO 全局（非功能）
来源 — 三方
CH 各处的 ProfileEvents / CurrentMetrics / fiu_do_on 在 Velox 均为 // TODO 占位。影响监控、容量诊断、故障注入，不影响核心算法账目。

已核验一致 / 剔除的假阳性

  • LRUFileCachePriority::canFit 两边逐字一致；LRU/SLRU/Split/EvictionCandidates 队列移动、候选账目、边界比较未见可证实的算法不一致。
  • FileSegment 状态机全部转换（getOrSetDownloader / resetDownloadingStateUnlocked / complete / shrink / setDetachedState / assertCorrectnessUnlocked）逐行一致。
  • FileCache::tryReserve / doTryReserve 主流程一致：HoldSpace / EvictionCandidates 提交回滚、catch(...) 僵尸条目 invalidate 保护、锁顺序 cacheStateGuard → cacheGuard.writeLock。
  • range() 闭区间语义（right inclusive，+1 转开区间）无 off-by-one；downloadFromReader 的 reserve-先于-consume 不变量成立，无丢字节风险。
  • 所有默认常量逐项相符（32MiB 段、4MiB 对齐、SLRU 0.6、max_elements 1e7 等）；FileCacheUtils roundUp/roundDown 数学一致。
  • 剔除的假阳性：后台下载「未 reset reader/downloader」实由 complete() 完成；WriteBufferFromFile 无 O_TRUNC + lseek 到末尾，不截断；错误码折叠为 VELOX_FAIL 属正常适配。
